Python · Beginner Lecture

Decorators are just gift wrap
for your functions.

You don't change what's inside the box. You wrap something extra around it — and every time someone opens it, they get the original gift plus the wrapping experience. That's exactly what a Python decorator does to a function.

step 1

Why do decorators even exist?

Imagine you're running a small restaurant. You have several functions in your kitchen code:

kitchen.py
def cook_pasta():
    print("Cooking pasta...")

def cook_pizza():
    print("Cooking pizza...")

def cook_soup():
    print("Cooking soup...")

One day your manager says: "I want to know how long every dish takes to cook, and I want every dish logged for our records."

The tempting — but bad — solution is to edit every single function:

kitchen.py — the messy way
import time

def cook_pasta():
    start = time.time()
    print("LOG: starting cook_pasta")
    print("Cooking pasta...")
    print("LOG: finished in", time.time() - start, "seconds")

def cook_pizza():
    start = time.time()
    print("LOG: starting cook_pizza")
    print("Cooking pizza...")
    print("LOG: finished in", time.time() - start, "seconds")

# ...and again, and again, for every dish
Real-life analogy

This is like asking every chef to personally staple a timer and a notepad to their apron before cooking anything — and repeating that instruction to every new chef who joins. It works, but it's repetitive, easy to forget, and a nightmare to update. If the manager later says "log it differently," you have to go back and edit every single recipe function.

What we actually want is a plating station: one place, standing between "the dish is cooked" and "the dish reaches the customer," that adds the logging and timing automatically — without the chef changing how they cook at all.

That "plating station" is what a decorator is. It's a piece of code that wraps around another function, adding behavior before and/or after it runs, without touching the original function's code.

step 2

The idea decorators are built on: functions are objects

In Python, a function is not a special, untouchable thing. It's an object — just like a number, a string, or a list. That means you can:

  • Assign a function to a variable
  • Pass a function as an argument into another function
  • Return a function from another function
first_class.py
def greet():
    return "Hello!"

# assign the function itself (no parentheses!) to a variable
say_hello = greet
print(say_hello())     # Hello!

def shout(func):
    # func is just a function passed in, like passing a number
    return func().upper()

print(shout(greet))    # HELLO!
Real-life analogy

Think of a function like a recipe card, not a finished dish. You can hand someone the recipe card (pass it as an argument), photocopy it and give it a new label (assign it to a new variable), or even hand a new recipe card back to someone (return a function). The card itself is just an object you can move around — it only "cooks" when someone actually calls it with ().

This is the one prerequisite fact that makes decorators possible. If functions couldn't be passed around like this, decorators simply couldn't exist.

step 3

Functions that live inside functions

You can also define a function inside another function. The inner function even remembers the variables of the outer function after the outer one has finished — this is called a closure.

nested.py
def outer():
    message = "I'm from the outer function"

    def inner():
        print(message)   # inner "remembers" message

    return inner   # return the inner function itself, not its result

my_func = outer()   # my_func is now the "inner" function
my_func()            # I'm from the outer function
Real-life analogy

This is like a manager (outer) briefing an employee (inner) before they leave the office. Even after the manager's meeting is over, the employee still remembers the instructions they were given. That "memory" travels with the employee wherever they go — just like inner still remembers message.

step 4

Building the plating station by hand

Now let's combine both ideas — passing a function in, and defining a function inside a function — to build our own "plating station" for the kitchen problem.

plating_station.py
import time

def log_and_time(func):          # takes a function in...
    def wrapper():
        print(f"LOG: starting {func.__name__}")
        start = time.time()
        func()                    # ...runs the ORIGINAL function...
        elapsed = time.time() - start
        print(f"LOG: finished in {elapsed:.4f}s")
    return wrapper                # ...and hands back a new, upgraded function

def cook_pasta():
    print("Cooking pasta...")

# manually wrap cook_pasta with the plating station
cook_pasta = log_and_time(cook_pasta)

cook_pasta()
# LOG: starting cook_pasta
# Cooking pasta...
# LOG: finished in 0.0000s
cook_pasta
→
log_and_time(cook_pasta)
→
new cook_pasta (wrapped)

Nothing about the original cook_pasta function changed. We only wrapped it. The line cook_pasta = log_and_time(cook_pasta) is the whole trick — log_and_time is a function that takes a function and returns a new, "decorated" function.

That line is exactly what a decorator does. We've just written it out longhand.

step 5

The @ symbol: syntax sugar, nothing more

Writing cook_pizza = log_and_time(cook_pizza) under every single function would get repetitive again. So Python gives us a shortcut: put @log_and_time directly above the function definition.

kitchen.py — the decorator way
@log_and_time
def cook_pasta():
    print("Cooking pasta...")

@log_and_time
def cook_pizza():
    print("Cooking pizza...")

@log_and_time
def cook_soup():
    print("Cooking soup...")

cook_pizza()
# LOG: starting cook_pizza
# Cooking pizza...
# LOG: finished in 0.0000s
Key insight

@log_and_time above def cook_pasta(): means exactly the same thing as writing cook_pasta = log_and_time(cook_pasta) right after the function. The @ is not magic — it's just a shorter way to say "pass this function through that other function, and replace it with the result."

Now every dish gets timing and logging for free, and if the manager wants the logging format changed, you edit one function — log_and_time — instead of every recipe.

step 6 · real example

The nightclub bouncer

Let's use a second, very intuitive analogy: a nightclub bouncer checking IDs at the door.

Real-life analogy

The DJ, the bartender, and the dance floor don't check anyone's age — that's not their job, and you don't want to rewrite "check ID" logic into every single activity inside the club. Instead, there's one bouncer at the entrance who checks everyone before they're allowed in. Every activity inside benefits from the same security check, defined in exactly one place.

club.py
def requires_id_check(func):
    def bouncer(name, age):
        if age >= 18:
            print(f"Bouncer: {name}, you're in.")
            return func(name, age)
        else:
            print(f"Bouncer: Sorry {name}, you're too young.")
    return bouncer

@requires_id_check
def enter_dance_floor(name, age):
    print(f"{name} is dancing!")

@requires_id_check
def enter_bar(name, age):
    print(f"{name} is ordering a drink.")

enter_dance_floor("Rafi", 22)   # Bouncer: Rafi, you're in. / Rafi is dancing!
enter_bar("Nadia", 15)          # Bouncer: Sorry Nadia, you're too young.

This is precisely how authentication decorators work in real web frameworks like Flask or Django — a single @login_required decorator guards dozens of different pages without any page needing to know how login checking works.

step 7 · real example

The stopwatch that fits any task

Back to timing — but now let's make it reusable for any function, with any number of arguments, using *args and **kwargs ("give me whatever arguments were passed, I don't need to know how many").

stopwatch.py
import time
from functools import wraps

def timer(func):
    @wraps(func)                 # keeps the original function's name & docstring
    def wrapper(*args, **kwargs):
        start = time.time()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.time() - start:.4f}s")
        return result
    return wrapper

@timer
def brew_coffee(size="medium"):
    time.sleep(0.2)
    return f"{size} coffee ready"

print(brew_coffee("large"))
# brew_coffee took 0.2001s
# large coffee ready
Why @wraps(func)?

Without it, brew_coffee.__name__ would report "wrapper" instead of "brew_coffee" — because that's genuinely the new function's name. functools.wraps copies over the original name and docstring so debugging tools and documentation still make sense. It's a small courtesy, but professional code always includes it.

step 8

Decorators that take their own arguments

Sometimes you want to configure the decorator itself — for example, retrying a function a specific number of times. That needs one extra layer of wrapping: a function that returns a decorator.

retry.py
def retry(times):                    # 1. takes the decorator's own argument
    def decorator(func):             # 2. this is the real decorator
        def wrapper(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    print(f"Attempt {attempt} failed: {e}")
            print("All attempts failed.")
        return wrapper
    return decorator

@retry(times=3)
def unstable_connection():
    import random
    if random.random() < 0.7:
        raise ConnectionError("timed out")
    return "connected!"

unstable_connection()
Real-life analogy

This is like telling the bouncer "give each guest up to 3 chances to find their ID before turning them away" — the number 3 is a setting you hand to the bouncer's instructions, not something baked permanently into how bouncers work in general.

step 9

Decorators you'll meet immediately in real Python code

You don't have to write every decorator yourself — Python and its libraries ship with several extremely common ones:

DecoratorWhat it does
@staticmethodMarks a method inside a class that doesn't need access to the instance (self) at all.
@classmethodPasses the class itself (cls) instead of an instance — often used for alternative constructors.
@propertyLets a method be accessed like a plain attribute, e.g. obj.age instead of obj.age().
@functools.lru_cacheAutomatically remembers previous results, so calling the same function twice with the same input skips the work.
@app.route(...)(Flask) Registers a function as the handler for a specific web URL.

Every single one of these follows the exact pattern you just learned: a function wraps another function (or method) and changes how it behaves, without rewriting its internals.

recap

Summary — what to remember

01

The problem

You need the same "extra behavior" (logging, timing, security checks) around many different functions, without copy-pasting code into each one.

02

The foundation

Functions are objects in Python — they can be passed around, stored in variables, and returned from other functions.

03

The mechanism

A decorator is a function that takes a function, defines a new inner function that wraps it, and returns that wrapper.

04

The syntax

@my_decorator above a function definition is shorthand for func = my_decorator(func). Nothing more mysterious than that.

05

The habit

Always use *args, **kwargs in your wrapper so it works with any function signature, and always add @functools.wraps(func).

06

The payoff

Change the "plating station" once, and every wrapped function updates automatically — logging, security, caching, retries, routing, and more.

Try it yourself

Write a decorator called @shout that makes any function's string return value come back in ALL CAPS with three exclamation marks — then apply it to a function that returns a greeting. That's the entire mental model you need, applied one more time.
